I spend a lot of time looking at how we build agents. Most research agents fail at the trust boundary, not the search box. We have plenty of tools that can wrap a search engine API and feed the results into a large language model. The problem is what happens next. A naive agent will read a few paragraphs, hallucinate a connection, burn through your API credits in a recursive loop, and present the resulting text as fact.

This is a systems engineering failure. When we build software that searches the web and reads documents, we cannot treat the large language model as an omniscient oracle. We have to treat it as an untrusted worker in a pipeline. Building an agent is not about granting a model unrestricted freedom. It is about defining strict constraints and forcing the model to prove its work at every step.

This brings me to Mole. Mole is a Go-based deep research agent [1]. It does not just search the web and summarize the first page it finds. It decomposes a question, searches for leads, reads sources, extracts claims, checks those claims against literal quotes, looks for contradictions, and writes an answer citing its work [1]. It exposes two static binaries, mole and mole-mcp, uses SQLite for storage, and requires Go 1.25 or later to build from source [1][14].

Installation alone does not give you a complete backend. You have to configure it with a search provider, like Brave or Tavily, and an LLM provider, like Anthropic or an OpenAI compatible service [14]. The README exposes `mole doctor` for checking the resulting setup, while the configuration loader supplies the provider settings and applies supported environment overrides [1][14]. The setup process has some friction because you must provide your own API keys for the model and the search provider. You are wiring up the backend infrastructure yourself, which is necessary for a tool that runs locally and manages its own execution budget.

Once configured, Mole operates as an evidence pipeline with a strict budget. It does not blindly fetch pages. The pipeline moves from question to answer through a very specific set of stages: planning, execution, claim extraction, quote verification, graph building, and output generation. Each stage is heavily guarded to prevent runaway execution.

The planner starts the process. By default, it generates four initial leads for a given question [2]. The planner does not just fire these off and wait. It operates on a cycle. It generates three new leads per replan, and it triggers a replan every three completed leads [2]. It caps the maximum depth at two [2]. The replan digest carries count metrics and planner wording to guide the next step [2]. It does not carry the raw fetched page text back to the planner, which prevents context window bloat and keeps the planning phase focused [2].

The executor queues and leases batches of leads to concurrent workers [3]. At the point where a lead is dispatched into actor work, it reserves a per-lead budget first. It uses cache hits where possible, settles every attempt, retries transient failures, and handles fatal errors without pretending they were successful [3]. It verifies state before triggering a replan [3]. This concurrency makes the agent fast, but concurrency without limits is dangerous.

The critical part of the execution engine is the ledger. Its invariant is reserve before dispatch and settle afterward [4]. The availability check and the hold happen in one transaction, so concurrent workers cannot all pass a stale balance. The append-only tool calls ledger is the source of truth for spend, while materialized session spend is updated in the same transaction [4]. Mole also holds a portion of the session budget in escrow for the report and final verification, so research cannot consume the money needed to explain its findings [4].

When a worker gets a lead, it hands it to the web actor. The web actor runs the search. It conditionally skips fetching a page if a provider already returned usable content in the search snippet [5]. Otherwise, it fetches the page and extracts the text [5].

The fetch and extraction guards are extensive. The web actor handles robots.txt rules, enforces per-domain rate limits, applies an SSRF and egress guard to redirects and resolved addresses, and denies requests to private networks or local domains [5]. It attempts to extract readable content or structured data [5]. It then chunks the text and uses a cheaper, faster model to mine claims from those chunks [5]. It persists these claims in the database.

However, you should keep these claims tied to the actor and the source code links. They are not a blanket security guarantee against all web exploits, but they do represent a serious effort to constrain the input [5]. Fetch failures and unusable extraction results are recorded as outcomes, so a blocked or malformed page remains distinguishable from a source that simply yielded no claims [5].

Mining a claim is easy. Proving it is hard. This is where the quote verifier steps in. The miner checks that each proposed claim has a source quote that appears in the source document [6]. The check first tries an exact match, then a whitespace-insensitive match; the stored span is the verbatim text from the source, not the model's rendering. It rejects quotes shorter than 24 characters after collapsing whitespace, and stored quotes are capped at 1200 characters [6]. The match also records a byte offset in the full source text.

This mechanism proves citation linkage. It proves that the document actually contains the words the model says it contains. It does not prove that the claim is true [6]. It only proves that the model did not invent the quoted span. A quote can still be selective or misleading, which is why the later graph and grounding stages exist.

After gathering claims and verifying quotes, Mole runs the verifier. The verifier builds a graph over all the extracted claims [7]. It retrieves candidate pairs of claims and adjudicates them in batches [7]. It optionally confirms the edges between these claims and derives a confidence score over the entire graph [7].

Crucially, the verifier can distinguish direct contradictions from evidence that is merely superseding or stale [7]. Because graph verification can be expensive, the system caps the verification spend at a default of 25 percent of the total session budget [7]. The cap keeps graph verification from consuming an unbounded share of the session, leaving room for the final report.

The project README publishes evaluation metrics, claiming zero percent budget overshoot, one hundred percent claim integrity, eighty percent grounding, and seventy percent contradiction precision [1]. I want to be clear that these are project-reported evaluation numbers. They are not measurements I have reproduced for this post. Still, the numbers reflect the priorities of the architecture: stay within budget and do not invent quotes.

What makes Mole particularly interesting is how it exposes this pipeline to other systems. This brings us to the Model Context Protocol, or MCP.

MCP changes the shape of how we interact with agents. Mole exposes its capabilities through autonomous MCP tools: research.report, research.status, research.result, research.cancel, research.ask, and research.sessions.list [8].

The flow is asynchronous. When a client calls research.report, the tool returns a session ID immediately [8]. The daemon continues the research session in the background. The client must poll research.status and eventually research.result to get the final output [8]. The research.ask tool provides a retrieval-only interface against already collected claims, performing no new searches or fetches [8].

Mole achieves this through a specific architecture. The daemon listens on a Unix socket inside a private directory, sets the socket to mode 0600, and checks the peer identity [12]. The mole-mcp binary is intentionally designed as a tiny stdio byte-forwarding shim [13]. It does not parse MCP frames itself. It writes all its diagnostics to stderr so that stdout remains clean and open for the protocol channel [13].

This explains the installation architecture. It explains why an MCP client configuration file contains a command to run the shim rather than API credentials [12][13]. The shim talks to the socket, and the daemon does the heavy lifting. This separation of concerns means the MCP client does not need to know anything about the database or the API keys.

Mole also offers a toolkit MCP mode [9]. This mode creates a second surface area. In toolkit mode, the host agent's model does the reasoning and planning. Mole simply supplies deterministic retrieval, quote checking, graph helpers, and local-data aggregation [9].

The source code explicitly notes that in toolkit mode, the prompt-injection fence becomes a convention, because the fetched text lands in a prompt that Mole does not assemble [9]. Toolkit mode enforces a 500-call ceiling for its own searches and fetches, but it cannot bound the host agent's own model usage [9].

Another critical boundary in Mole is how it handles local data. Local data is a completely separate path from web search.

If the model decides it needs local data, it selects a hypothesis template and column names, but it does not author SQL or see raw rows [10]. Mole renders the statement, runs it through a read-only connector, passes it through a SQL guard and an aggregation gate, and sends only the resulting aggregate envelope back [10][11].

The privacy gate defaults include a k-anonymity floor of 5, a maximum raw row count of 5000, a TopK limit of 25, and a strict withholding of free-text columns [11]. Every crossing of this boundary is logged [11].

You must be clear that aggregates still disclose information. This gate is a boundary, not magic. It prevents row-level text from crossing, but statistical disclosure is still possible [11]. The useful property is that the rules are explicit and the crossing is auditable.

Setup requires configuration. The README describes config.json in the user configuration directory, with a 0700 directory and a 0600 file, and no credentials in the MCP JSON file [1][14]. The source loader also supports environment overrides and lets them replace file values, so the file is the normal persistent store rather than the only input [14].

This separation keeps API keys out of the client configuration, but it is not a claim that environment variables are impossible or automatically safe. Container deployments can provide supported settings through the environment [14]. `mole serve` loads the configuration and builds the web actor before it calls the daemon's socket listener. Missing search or LLM provider setup fails before the socket is created, rather than leaving a daemon advertising a backend that cannot run [14].

When you look at the whole system, you see what Mole gets right. It treats token generation as a hazard to be managed, not a free resource. It forces claims to be grounded in verbatim quotes. It separates the execution daemon from the MCP shim. It puts a hard wall between web search and local data aggregation.

Its guarantees do not mean the system is flawless. A verbatim quote can still be taken out of context. A claim can be perfectly cited from a source that is entirely wrong. The local data gate prevents reading individual rows, but it does not prevent all forms of data inference. The burden of trusting the final output still rests on the user reading the citations.

But this is the right way to build a research agent. A research agent is an evidence pipeline with a budget, not a search wrapper. It is a system that must operate within strict technical boundaries, manage its resources carefully, and prove its work.

Mole demonstrates a practical pattern: constrain the model, enforce quote integrity, and manage the budget transactionally, then expose the result behind a daemon that can keep working after a client call ends. That is more disciplined than solving research quality with a larger context window.
